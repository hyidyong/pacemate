# Stage 2 — Availability Domain Design

Evidence sources: Stage 1 docs (SLOT_DATAFLOW.md, SLOT_BUG_REPRODUCTION.md), plus a fresh
4-agent read-only discovery sweep on 2026-08-12 at `upgrade/stage-2` base d922b34
(consumers, reservation semantics, time semantics, test coverage). All file:line refs
verified against current source.

## 1. Current problem

Availability semantics live in two independent engines plus scattered policy fragments:

- **Engine A (canonical)** — `buildAvailableCounselingSlots` (src/lib/counseling-slots.ts:74).
  Declared `professor_availability` windows → slot_minutes chunks, days +1..+14, weekdays,
  ≤18:00 KST, minus teaching/admin/blackout-date/busy(pending+approved)/inactive-overlap.
  Asia/Seoul-correct (Intl two-pass). Drives the student page AND the authoritative booking
  re-validation (`counseling.actions.ts:33-41`) + DB GiST exclusion constraint.
- **Engine B (duplicate)** — `calculateRecommendedAvailability` (src/lib/calendar-utils.ts:27).
  Hard-coded Mon–Fri 09:00–18:00 30-min grid; labels ALL free time "상담 가능/상담 예약이
  가능한 시간입니다" even with zero declared windows (0-vs-85 mismatch, reproduced in
  Stage 1); browser-local `Date` methods; no horizon; busy time = `suggested ?? requested`.
- **Policy fragments** — `scheduling-policy.ts` (browser-local helpers, 4 of 7 exports
  unused), `STUDENT_BOOKING_END_HOUR` defined 3×, `timeToMinutes` 3×, `__BLACKOUT__` parsed
  3 ways (strict regex in engine A; loose `split("__")[2]` in engine B and
  professor-calendar.tsx), local-date-key formatter ~6×.

## 3. Domain vocabulary (from repository evidence — nothing invented)

- **Slot**: identified by `(professorId, start instant, end instant)`. No location/resource/
  tenant/capacity dimensions exist. Canonical id = `getCounselingSlotId` (to be normalized
  per V6).
- **available == bookable**: a slot generated by engine A. There is no role-based subset:
  every generated slot is offered to every student and is exactly what the booking path
  re-validates. `visible` is not a separate concept in this product.
- **blocked**: time covered by an `is_active=false` availability row or a
  `__BLACKOUT__YYYY-MM-DD` admin task.
- **undeclared free time** (professor calendar only): time with no busy occupancy and no
  declared window. NOT student-bookable. Today mislabeled "상담 가능" (the KI-001 defect).
- **remaining / full**: no numeric capacity exists anywhere (confirmed: zero hits in src/ and
  supabase/ for capacity/정원/seats). Capacity is structurally 1 per (professor, timerange)
  via the GiST exclusion constraint. `remainingCapacity` is therefore NOT modeled; slot
  existence == bookable.
- **expired/past**: engine A generates only days +1..+14 from KST today; past/today slots are
  never produced (offset starts at 1 — this IS the same-day cutoff; no other cutoff exists).

## 4. Reservation status semantics (verified contract)

DB enum `counseling_status`: exactly `pending | approved | rejected | cancelled`
(migration 20260703035228:10). No `completed`. Phantom values
`answered/ANSWERED/PENDING` exist only in the `ProfessorCounselingRequest` TS type
(professor.service.ts:64) and `"scheduled"` in dashboard/page.tsx:215 — unreachable noise.

| Status | Consumes slot? | Bookable again? | Student UI | Professor UI | Transitions |
|---|---|---|---|---|---|
| pending | YES (busy filter + GiST constraint) | no | "승인 대기" | pending inbox (amber) | → approved / rejected / cancelled via `updateCounselingStatus` (professor/assistant) |
| approved | YES (busy filter + GiST constraint) | no | "승인 완료" | calendar block + log (green) | → cancelled (calendar 일정 취소) |
| rejected | NO — slot frees up | yes | "시간 조정" + 추천 시간 re-book | log (red) | terminal in practice |
| cancelled | NO — slot frees up | yes | "취소됨" | log (red) | terminal in practice |

- Insert path: `createCounselingRequest` → always `pending` (student only).
- No student-facing cancel exists (verified — no action, no UI).
- `suggested_start/end`: written only by the reject flow (start + hard-coded 30 min);
  advisory only — NOT covered by the exclusion constraint, NOT in the busy filter. In
  practice non-null only on `rejected` (approve/cancel overwrite them to null,
  professor.actions.ts:224-229). Canonical busy time is therefore `requested_*` only (V5
  resolution — matches engine A and the DB constraint).

## 5. Capacity semantics

`capacity = 1` per (professor, time range), enforced by
`counseling_requests_no_active_overlap` (GiST, `tstzrange(requested_start,requested_end,'[)')`,
`WHERE status IN ('pending','approved')`) + older exact-match partial unique index.
`remainingCapacity`/`isAvailable`/`isBookable` collapse to one boolean: the slot exists in
the canonical output. Stage 2 does not introduce a numeric capacity model.

## 6. Time semantics

- Canonical zone: `PACEMATE_TIME_ZONE = "Asia/Seoul"`. No date library; no TZ env config;
  Vercel serverless runs UTC — all browser/server-local Date logic is wrong outside KST.
- Normalization boundary: **the domain module** (src/lib/counseling-slots.ts). All
  wall-clock↔instant conversion happens there via the existing Intl two-pass helpers;
  consumers exchange either instants (ISO strings) or KST wall-clock parts obtained from
  exported helpers.
- Interval semantics: half-open `[start, end)` at every layer (rules, engines, DB
  constraint) — verified consistent; preserved.
- Booking window rules (horizon +1..+14, weekday-only, ≤18:00 end cap, 48-slot cap) live
  only in the domain module.
- Week convention: Sunday=0 integers (DB + engines); professor calendar renders Monday-first
  (presentation only).

## 7. Canonical availability contract

```ts
// Domain module: src/lib/counseling-slots.ts (single source of truth)

// Existing, unchanged public shape (API compatibility):
buildAvailableCounselingSlots(input): CounselingSlot[]   // student page + booking authority

// New: shared per-date primitive (used by both consumers) — internal detail exported
// for the professor-week adapter and tests:
buildBookableSlotsForLocalDate(date: LocalDate, input): CounselingSlot[]
//   = declared active windows matching the date (specific_date wins over day_of_week)
//     → slot_minutes chunks ending ≤18:00, minus teaching/admin/blackout-date/
//       busy-request(requested_*, pending+approved)/inactive-window overlaps.
//   buildAvailableCounselingSlots ≡ weekday-filtered union over today+1..today+14, deduped,
//   sorted, capped 48.

// New: professor week view adapter (src/lib/calendar-utils.ts):
buildProfessorWeekAvailability(weekDateKeys, input): {
  bookableSlots: CounselingSlot[]            // canonical slots for the displayed dates
  chunks: Array<{                            // 30-min display grid (presentation)
    day: 1..5; specificDate: "YYYY-MM-DD";
    start: "HH:MM"; end: "HH:MM";
    kind: "bookable" | "blocked" | "free";   // free = undeclared, NOT student-bookable
    id?: string;                             // availability-row id for the toggle flow
  }>
}

// Exported time helpers (one normalization boundary):
getLocalDateKeyInTimeZone / addLocalDays / getDayOfWeek / dateKeyToLocalDate /
localDateTimeToInstant / instantToLocalParts / timeToMinutes / minutesToTime /
parseAdminBlackoutDate / STUDENT_BOOKING_END_HOUR / timeRangeEndsByStudentCutoff
```

The contract answers: slot identity (professorId+start+end, normalized ISO); visibility
(= existence); bookability (= existence, re-validated server-side + DB constraint);
capacity (structural 1); reason-unavailable (professor grid: blocked vs free vs busy);
statuses that matter (pending+approved on `requested_*`); time rules (KST, half-open,
horizon/cutoff in domain only). No `reasonUnavailable` enum for students is introduced —
the current product never surfaces one (YAGNI).

The **horizon (+1..+14) is a booking-window rule, not a property of the weekly schedule**:
the professor grid classifies a chunk "bookable" iff canonical rules would emit that slot
for that date; the student list additionally applies the horizon. The regression invariant
compares dates inside the horizon, where the two must match exactly.

## 8. Approaches evaluated

### Approach A — extract shared per-date primitive in the existing domain module; rewrite calendar-utils as a thin adapter (CHOSEN)
- counseling-slots.ts already is the canonical module (pure, tested, KST-correct, imported
  by client and server). Extract the per-date slot computation it already performs inside
  its loop; `buildAvailableCounselingSlots` keeps byte-identical output (protected by
  characterization tests). calendar-utils.ts keeps its file path/import surface but its
  engine becomes a consumer of the primitive.
- Correctness: single computation path. Migration risk: low (one consumer at a time; both
  engines' outputs test-frozen first). Testability: pure functions, node:test as today.
  Churn: minimal. Compatibility: public signatures preserved. Stage 5: pure domain +
  unchanged DB constraint is the right substrate. Multi-tenant: pure inputs, no global state.

### Approach B — promote the server service (counseling.service.ts) to compute the professor week view server-side
- Would centralize data loading (fixing V3/V4 naturally) but moves the week grid to the
  server: week paging (prevWeek/nextWeek, professor-calendar.tsx:69-83) would need a server
  round-trip per navigation — a UX behavior change, more churn (props/page contract), and
  couples the domain to RSC. Rejected: violates "preserve UI/UX", larger blast radius.

### Approach C — application-level facade over both existing engines
- A facade cannot make two divergent engines agree; it preserves two sources of truth and
  adds a third surface. Rejected: does not achieve the stage goal.

## 9. Migration strategy (one consumer at a time)

1. Characterization tests extend coverage of engine A (horizon boundaries, weekend, blackout
   dates, slot_minutes granularity, specific_date, cap 48, cross-professor isolation) — no
   behavior change.
2. Slot-id normalization (V6): RED test (ids from `+00:00` vs `.000Z` forms must match) →
   GREEN in `getCounselingSlotId`. Booking authority + workspace + reserveSuggested all go
   through this one function.
3. Internal refactor of engine A around `buildBookableSlotsForLocalDate` — characterization
   suite must stay green (no RED expected; pure refactor).
4. Professor week adapter: contract tests RED against the ported legacy semantics (zero
   declared rows must yield zero bookable chunks — currently ~85) → GREEN implementation on
   the canonical primitive. Includes KST week-date derivation and V5 (requested_* only).
5. Data adapter fixes: professor.service.ts selects `specific_date` (V4) and provides the
   calendar a complete pending+approved busy feed (V3) while the management list query stays
   untouched.
6. professor-calendar.tsx migration: consume the new adapter; KST helpers for week dates,
   blackout date matching, and approved-block times (V2); three-state chunk labels — the
   minimal honest UI delta (see §11).
7. Policy consolidation: move `timeRangeEndsByStudentCutoff` + weekday-of-date-key
   validation into the domain; migrate professor.actions.ts; suggested-time input parsed as
   KST wall clock (V7); today-timetable-widget weekday via KST helper (V8); delete
   scheduling-policy.ts (4 of 7 exports already dead, remainder migrated).
8. Cross-consumer regression test (§10) + removal of the now-unused legacy engine path.

Each step: targeted tests → full suite → commit.

## 10. Cross-consumer regression invariant (exit-gate #28/29)

One synthetic dataset (active/inactive/specific-date windows, teaching, admin + blackout
tasks, requests in all four statuses). Assert, for dates within the horizon:

- set of canonical slot ids from `buildAvailableCounselingSlots`
  == set of slot ids from `buildProfessorWeekAvailability(...).bookableSlots`
  (identity comparison: professorId + start + end instants — not counts);
- no grid chunk classified `bookable` outside those slots' time cover, and none classified
  `free`/`blocked` inside it;
- booking authority consumes `getAvailableCounselingSlots` (same engine A output) — its
  eligibility is definitionally the same set; the slot-id normalization test protects the
  id-matching step it relies on.

## 11. Compatibility strategy

- Public/API surfaces preserved: `buildAvailableCounselingSlots` signature and output,
  `CounselingSlot` type, `CounselingPageData`, server-action signatures, routes, JSON field
  names, DB schema (no migrations).
- `calculateRecommendedAvailability` is replaced by the new adapter; its import site
  (professor-calendar.tsx) migrates in the same commit; the two Stage 1 regression tests
  (pending-blocks, inactive-hour-blackout) are re-expressed against the new adapter with
  identical semantics.
- Intentional, authorized UI delta (KI-001 correctness fix, not a redesign): undeclared free
  chunks change label "상담 가능" → "상담 미개방" (details: 학생에게 예약 가능으로 공개되지
  않은 시간) with a neutral tint; declared-bookable chunks keep "상담 가능" exactly. Grid
  layout, block geometry, dialogs, and interactions unchanged. Stage 4 owns any further
  presentation work.
- Internal type additions (ProfessorAvailability.specific_date, new calendar prop) are
  non-breaking; phantom status values are narrowed to the DB enum.

## 12. Risks

- R-1: Refactor of engine A changes output subtly → mitigated by characterization-first and
  byte-level slot assertions.
- R-2: Calendar visual regression → mitigated by keeping chunk geometry and rendering QA
  (desktop + 375px) before/after.
- R-3: V3 busy-feed change alters what the management list shows → mitigated by leaving the
  list query untouched and adding a separate calendar feed.
- R-4: KST week derivation shifts the displayed week for non-KST browsers (intended
  correctness change; KST browsers unaffected).
- R-5: Slot-id normalization changes ids embedded in client state mid-deploy → ids are
  ephemeral (page-lifetime), no persistence; risk negligible.
- R-6: `.superpowers/` untracked dir and codex worktrees exist in the repo — untouched.
